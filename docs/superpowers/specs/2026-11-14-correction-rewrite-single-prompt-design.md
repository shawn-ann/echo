## 一、背景

现有纠错链路为：`POST /api/v1/messages` 触发一次 LLM 调用，返回 `has_errors`、`errors[]` 和 `rewrite`（minimal / natural）；纠错成功后由 `BackgroundTasks` 异步调用第二个提示词生成笔记（`knowledge_point` 等）。

曾评估将「纠错、改写、知识点」拆成 3 个提示词并陆续返回，主要理由是：

1. 提示词职责分离，避免内容过多互相干扰；
2. 不必等待全部完成才返回，缩短长等待。

分析后确认：

- **纠错与改写强耦合**：`rewrite.minimal` 的定义就是「把 `errors` 中的 `correction` 应用到原文」。拆开后改写仍须以 errors 为输入串行执行，否则会出现纠错与改写不一致；串行还会拉长总耗时。
- **笔记本来就是独立且异步的**：`routers/messages.py` 在返回报告后通过 `BackgroundTasks` 触发 `note_service.save_notes`，不阻塞用户。
- **感知延迟的正解是流式返回**，而不是增加调用次数；单次调用同样可以按固定字段顺序分节流式输出。
- 不同阶段使用不同温度/模型确有价值，但属于独立的「按用途配置 LLM 参数」优化，不是拆分提示词的充分理由。

因此决定维持「纠错 + 改写单提示词、笔记异步」的现有形态。

## 二、决策

| # | 决策 |
|---|------|
| D1 | 纠错与改写共用**一次 LLM 调用、一个提示词、一个温度**；推荐 `LLM_TEMPERATURE=0`，改写的地道程度由提示词约束保证。 |
| D2 | 笔记（`knowledge_point`、`alternatives`、`feynman_question`、`change_details` 等）继续**异步生成**，不阻塞纠错响应。 |
| D3 | **不引入** 3 提示词并行方案；**不拆分** `rewrite.minimal` 与 `rewrite.natural`。 |
| D4 | 笔记异步失败当前仅记录日志，**用户可见性**列为后续可选优化，不在本次范围。 |
| D5 | 按用途区分模型/温度/thinking 的 **per-task LLM profile** 不在本次范围，作为后续独立优化项。 |

## 三、方案对比

| 方案 | 做法 | 延迟 | 一致性 | 成本/复杂度 | 结论 |
|------|------|------|--------|-------------|------|
| **A（选定）** | 单提示词同步产出 errors + rewrite；笔记异步 | 首屏为一次调用耗时；笔记不阻塞 | 最高，改写直接基于同次纠错结果 | 最低，沿用现有实现 | **采纳** |
| B | 拆为「纠错 → 改写」两段串行，先返回 errors | 首包更早，但总时长增加 | 依赖 errors 传递，需额外校验 | 中，接口与契约需改 | 备选，出现明确问题时再启用 |
| C | 纠错、改写、知识点 3 个提示词尽量并行 | 未必更快（3 次排队/预填充） | 最差，容易各说各话 | 最高 | 不采纳 |

选择 A 的核心理由：在保证纠错与改写一致性的前提下，复杂度和成本最低；且它正是当前已实现的形态，不需要改接口、数据库和前端主链路。

## 四、与现有实现的对照

本决策**不产生代码改动**，现状即目标状态：

- `backend/app/services/correction_service.py`：`submit_message` 单次调用 `_call_and_parse`，解析 `CorrectionBody`（`errors + rewrite`）。
- `backend/app/routers/messages.py`：`has_errors=true` 且存在 `rewrite.minimal.text` 时，注册 `_run_note_save_async` 后台任务。
- `backend/app/services/note_service.py`：独立提示词与独立会话，异步生成笔记。
- `backend/app/core/config.py`：纠错与笔记当前共用全局 `LLM_MODEL` / `LLM_TEMPERATURE` / `LLM_ENABLE_THINKING`。

## 五、范围

**做**

- 以本文档作为纠错/改写/笔记提示词边界的决策基线。
- 后续相关改动需说明是否偏离本决策。

**不做**

- 拆分纠错与改写提示词。
- 引入多调用并行或 3 提示词流水线。
- 流式返回（SSE）。
- 按用途区分 LLM 参数的 profile 抽象。
- 笔记异步完成/失败的前端可见性改造。

## 六、风险与后续触发条件

| 风险 | 触发信号 | 后续动作 |
|------|----------|----------|
| 单温度导致改写套路化、重复 | 线上反馈或评测显示 natural 表达趋同 | 启用方案 B：先返回 errors，再以 errors 为输入生成改写，提高改写温度 |
| 用户仍感知等待过长 | TTFT / 端到端时长超出预期 | 在单提示词内按 `has_errors → errors → rewrite` 固定字段顺序做流式分节返回 |
| 笔记生成失败用户无感知 | 后台日志出现连续失败 | 增加笔记状态事件或前端轮询 |
| 纠错与笔记需要不同模型/温度 | 成本或质量评估提出要求 | 引入 per-task LLM profile（本次 D5 已预留） |
